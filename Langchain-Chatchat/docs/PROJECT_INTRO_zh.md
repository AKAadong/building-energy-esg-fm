# 建筑能源 ESG-FM 智能知识问答项目 — 简介与创新说明

本文档面向评审、合作方与新人，概述**项目定位**、**创新点及体现方式**、**技术路线**与**交付形态**。代码与镜像以仓库 **`AKAadong/building-energy-esg-fm`**（`dev-ai` 等分支）为准。

---

## 一、项目简介

本项目在开源框架 **Langchain-Chatchat** 之上，面向**建筑能源、ESG、设施管理（FM）**等业务场景，构建**可私有化部署**的**检索增强生成（RAG）**与**对话式知识服务**。系统支持将 PDF、文档等资料入库并向量化，结合大语言模型（LLM）与嵌入模型（Embedding）完成**领域问答、知识库检索与多轮对话**；同时提供 **HTTP API** 与 **Web 管理界面**，便于与现有业务系统或前端集成。

**典型用途包括**：内部规范与标准查询、能源与碳排相关条文辅助解读、运维与资产文档检索、团队知识沉淀与对外演示等。

**交付形态**：

- **源代码**：Git 托管，按角色分支协作（如 `dev-ai`、`dev-backend`、`dev-frontend`）。
- **容器镜像**：通过 **GitHub Actions** 构建并发布至 **GHCR**（`ghcr.io`），便于一键拉取与部署。
- **文档**：接口说明、部署指南、知识库优化与可选 **SFT 微调**流程说明。

## 二、创新点与体现方法

以下创新点强调**在本项目中的落地方式**；其中部分为工程化增强，部分为领域应用组合创新。

### 1. 领域知识与大模型协同（RAG + 业务语料）

| 创新点 | 说明 | 体现方法 |
|--------|------|----------|
| **行业语料驱动的问答** | 不仅依赖通用大模型，而是将建筑能源 / ESG / FM 相关 PDF、制度与内部文档入库，回答**可追溯至检索片段**。 | 使用知识库创建、文档上传、向量检索与 **知识库对话 API**；在 Web 端「知识库管理」「RAG 对话」中演示。 |
| **可配置的检索策略** | 通过分段大小、`top_k`、相似度阈值等平衡**召回率与噪声**。 | 在配置与工具脚本中调参；可选检索评测脚本（如 hit-rate@k）量化效果。 |

### 2. 端到端私有化与可复现交付

| 创新点 | 说明 | 体现方法 |
|--------|------|----------|
| **容器化一键部署** | 将应用与依赖封装为镜像，降低环境差异。 | **Dockerfile** + **Compose**；文档中说明 `docker compose` 启动方式。 |
| **CI 自动构建与镜像注册** | 代码推送后自动构建并推送到 **GHCR**，版本与提交可追溯。 | **GitHub Actions**（`docker-build` 工作流）；Actions 与 **Packages** 页面可见成功构建记录与镜像标签。 |

### 3. 工程化增强（稳定构建与文档化）

| 创新点 | 说明 | 体现方法 |
|--------|------|----------|
| **适合 CI 的镜像构建策略** | 采用仓库内源码 + `pip` 安装等方式，减轻在云端长时间 `poetry install` 的失败率；可选增加 swap 等。 | Dockerfile 与 workflow 变更；Actions 构建日志。 |
| **对外 API 文档化** | 统一说明 REST 路径、Swagger 入口与 SDK 环境变量。 | `docs/API_REFERENCE_zh.md`、`docs/api/README_api.md`；运行时 **`/docs`**。 |
| **PDF 与入库体验** | 对 PDF 文本做基础清洗（如页眉页脚噪声），减轻检索噪声。 | `mypdfloader` 与配置项；大文件建议分批入库的操作说明。 |

### 4. 可选：领域模型能力延伸（SFT）

| 创新点 | 说明 | 体现方法 |
|--------|------|----------|
| **领域问答风格与术语** | 在 RAG 之外，可通过 **监督微调（SFT）** 让模型更贴合行业表述（如 Qwen2.5 系列）。 | `tools/sft/` 下脚本与说明；在 **Xinference** 等推理侧加载合并后的权重。 |

> 说明：**RAG 解决“知识从哪里来”**，**SFT 解决“怎么说得更像领域专家”**；二者可并行采用。

## 三、技术路线（技术栈）

### 1. 总体架构

```text
[客户端 / 业务系统]
        │ HTTP / OpenAPI
        ▼
┌───────────────────────────────┐
│  Chatchat API Server (FastAPI) │  ← 7861 默认
│  + Streamlit WebUI (可选)      │  ← 8501 默认
└───────────────┬───────────────┘
                │ OpenAI 兼容 API
        ┌───────▼────────┐
        │  Xinference 等  │  ← LLM / Embedding 推理
        │  模型推理服务     │
        └─────────────────┘
                │
        ┌───────▼────────┐
        │  向量库 (FAISS 等) │  ← 知识库嵌入与检索
        └─────────────────┘
```

### 2. 分层说明

| 层次 | 技术选型 | 作用 |
|------|----------|------|
| **应用框架** | FastAPI、Uvicorn | REST API、OpenAPI 文档、异步能力 |
| **对话与 RAG** | LangChain 生态、项目内 RAG 与 Agent 编排 | 链式检索、对话、工具调用 |
| **Web 管理端** | Streamlit | 知识库管理、对话界面、配置入口 |
| **推理** | Xinference（推荐）或其它 OpenAI 兼容服务 | 本地或远程部署 LLM / Embedding |
| **向量检索** | FAISS（默认常见）、可扩展其它向量库 | 文档切片嵌入后的相似度检索 |
| **嵌入与模型** | 如 bge 系列、Qwen 等 | 文本向量化与生成 |
| **配置与数据** | YAML、本地目录 `CHATCHAT_ROOT` | 模型与知识库配置持久化 |
| **容器与交付** | Docker、Docker Compose、GHCR、GitHub Actions | 构建、发布与部署标准化 |
| **可选微调** | PyTorch / PEFT / QLoRA 脚本（见 `tools/sft`） | 领域 SFT，与推理服务对接 |

### 3. 开发与协作

| 环节 | 工具 |
|------|------|
| 版本控制 | Git |
| 依赖管理（Python 库） | Poetry（`libs/chatchat-server`） |
| 镜像构建 | Dockerfile + CI |
| 接口调试 | Swagger `/docs`、`curl`、Python SDK |

### 4. 与上游关系

- **核心应用逻辑**基于开源项目 **Langchain-Chatchat**（`chatchat-space/Langchain-Chatchat`）。
- 本团队仓库在**配置、文档、工作流、领域脚本与镜像发布**等方面做增量；业务数据与模型权重由部署方自行管理。
